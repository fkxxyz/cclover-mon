# cclover-mon public API v1

The headless server and the interactive product expose one HTTP surface. `/api/v1/*` is the
machine-readable monitoring contract; the browser panel is served separately and is not part of it.

This document states the semantics the wire types cannot express. The Rust projection types in
`crates/cclover-http/src/api/` own the shape, and the process-row examples below are pinned by
`crates/cclover-http/src/api/tests.rs::process_rows_carry_identity_and_never_drop_a_row_for_a_missing_name`;
changing one without the other is a contract change. The reasoning behind the current shape is in
[ADR 017](../architecture/09-architecture-decisions/017-process-identity-and-ranking-ownership.md).

All endpoints are `GET`, return `application/json`, and require no authentication. They are served
only after the first real sample: before that, they answer `503` with `monitor state not ready`.
`/healthz` reports listener liveness, `/readyz` reports sampling readiness.

Split endpoints are views over the same projection as `/api/v1/state`. They never contain a metric
the full state does not contain, and they are not independently sampled.

## Observation envelope

Every metric is either a plain value or an observation status:

```json
{"status": "available", "value": 37.5}
{"status": "degraded",  "value": []}
{"status": "unavailable", "value": "permission_denied"}
```

`status` is one of `available`, `degraded`, `unavailable`. For `unavailable`, `value` is a reason:
`unsupported`, `disabled`, `permission_denied`, `unavailable`, or `invalid_data`. A successful empty
collection is `available` with `[]`; it is data, not failure. Clients must not read an unavailable
metric as zero.

## Process identity

Every process-facing row starts with the same identity object:

```json
"process": {"pid": 1234, "instance": "133012345678901234"}
```

- `pid` is the operating system process identifier. It is reused by the OS and is therefore not an
  identity on its own.
- `instance` is an opaque per-instance marker, as a decimal string. It is stable for the lifetime of
  one process instance and differs when a PID is reused. Compare it for equality only: its platform
  unit is unspecified, it is not a timestamp, and it must not be parsed or interpreted. It is a
  string because the underlying marker does not fit the exactly representable JSON number range on
  every platform.
- `name` is the observed process name, or `null` when metadata for that instance was not observed.
  Rows are never dropped for a missing name.

## Ranked process rows

Four row families. All are ranked, so an array position is meaningful.

CPU (`top_cpu`, and `top_cpu` in `/api/v1/processes`):

```json
{"process": {"pid": 42, "instance": "7"}, "name": "worker", "percent": 12.5}
```

`percent` is normalized so one fully busy logical CPU is `100`. A multi-threaded process can exceed
`100`, up to the logical CPU count times `100`.

Memory (`top_memory`, and `top_memory` in `/api/v1/processes`):

```json
{"process": {"pid": 42, "instance": "7"}, "name": "worker", "bytes": 4096}
```

`bytes` is resident memory (the working set on Windows), not private or virtual memory.

Disk I/O (`process_disk_io`, and `disk_io` in `/api/v1/processes`):

```json
{
  "process": {"pid": 42, "instance": "7"},
  "name": "worker",
  "disk_id": "disk-a",
  "device": "nvme0n1",
  "read_bytes_per_sec": 1.0,
  "write_bytes_per_sec": 2.0
}
```

Network I/O (`process_network_io`, and `network_io` in `/api/v1/processes`):

```json
{
  "process": {"pid": 42, "instance": "7"},
  "name": "worker",
  "network_id": "network-a",
  "interface": "eth0",
  "rx_bytes_per_sec": 8.0,
  "tx_bytes_per_sec": 16.0
}
```

`disk_id` and `network_id` are the opaque device identities used by `disks` and `networks`; join on
them, not on `device` or `interface`, which are display labels. Rates are per second over the last
sampling interval and are `0` on the first sample, where no interval exists yet.

### Ordering

Within one device, I/O rows are ordered by the sum of their two directional rates, descending. CPU
and memory rows are ordered by value, descending. Ties are ordered by ascending process identity
(`pid`, then `instance`), so a given payload is reproducible and clients may rely on position for
"top N".

### Row counts

The default payloads carry a fixed number of rows: 8 for CPU and memory, and 3 per device for disk
and network I/O. Array length is part of the v1 contract, not a sampling accident: a short array
means fewer ranked candidates existed, not that rows were withheld.

## Devices, sensors, and histories

Device and sensor entries carry an opaque `id` that is stable across renames and reboots, plus a
display `name`. Join on `id`. Disk entries expose a physical-device label and associated logical
labels; a drive-letter change does not create a new disk or reset its rate history.

History entries are bounded ring buffers with `history_capacity` as the capacity, keyed by the same
opaque identity used by the current snapshot. They are ordered oldest to newest.

## Compatibility

`/api/v1` is versioned as a whole. Additive changes (new fields, new endpoints) may appear in v1;
existing fields keep their meaning and type. Two deliberate breaking revisions exist so far, both
taken while the contract had no consumer outside this repository: process rows gained `process`,
CPU and memory rows gained `name` with `null` allowed, and the previous numeric `birth_marker` field
is gone; and the legacy `gpu-memory` snapshot and history endpoints were removed because GPU
snapshots already publish the same VRAM facts. An external consumer appearing would end this
freedom: from then on, a breaking revision needs a new version path.
