# Native Deployment

Each supported native target has two product artifacts built from the same workspace. `cclover-mon` is the interactive desktop/TUI application and may also expose HTTP. `cclover-mon-server` is the headless server artifact. Both remain single-process executables and share the platform collectors, sampling runtime, HTTP transport, metric model, and Web assets where applicable; the server artifact does not depend on desktop or terminal host crates.

Published distribution artifacts use the Cargo `dist` profile, which inherits the optimized `release` profile and sets `panic = "abort"`. A Rust panic is treated as an unrecoverable program defect, so shipped binaries terminate the process instead of paying for unwinding support. Normal development and validation continue to use their existing profiles and panic semantics.

`release.ts` is the repository release entry point and `tools/release/plan.ts` is the single release-plan authority. The plan declares both the supported publishable `ReleaseArtifact` set and required release-level companion assets, including product identity, Rust target, archive format, service assets, artifact naming, embedded third-party payloads, and source-fulfillment assets. `tools/release/build-context.ts` resolves one artifact-local build context: the build invocation and provenance facts for the same tool environment. `tools/release/source-retention.ts` owns acquisition and immutable retention of pinned corresponding-source Git graphs; it stores root/submodule bare shallow repositories under the shared dependency cache so shallow boundaries remain explicit, revalidates root commits and recursive gitlinks on every materialization, fetches upstream only on a cache miss, and fails closed on an existing corrupt entry. The same retention authority defines the representation-compatible cache path, immutable entry identity, current-plan cache key, compatible restore prefix, and pruning of entries no longer reachable from the current source plan. GitHub Actions obtains that machine-readable cache contract through `release.ts`, may restore an older snapshot only within the same representation schema, prunes obsolete entries before acquisition, and does not independently encode retention schema, layout, or source-plan identity. A dedicated default-branch source-retention cache workflow warms the current retained-source snapshot so tag-triggered releases can reuse the default branch's cache scope without making release-cache availability part of validation semantics; release correctness does not depend on a cache hit and still reacquires and verifies missing entries. `tools/release/redistribution.ts` consumes that single retained-source materialization path to project declared embedded payloads into notice/source mappings, deterministic corresponding-source archives, and source-fulfillment verification. `tools/release/pipeline.ts` executes build/staging/manifest aggregation, while `tools/release/archive.ts` owns product archive creation, archive-producer identity, and exact file-set verification; GitHub Actions consumes the entry point rather than reconstructing a product/target or fulfillment matrix. Each product build atomically compiles with the `dist` profile, stages its declared files, creates the archive, verifies the archive's exact file set against the plan, and emits a manifest containing product, version, target, Git commit, SHA-256, durable embedded-payload-to-companion-source fulfillment mappings, build-host identity, Rust/Cargo identity, and the native compiler, static archiver, linker driver/backend, archive, and compression tools that materially produce distributed bytes. Tool identity uses a stable version where available and an executable SHA-256 when the tool has no reliable version interface. Windows manifests additionally record cargo-xwin identity, the required `XWIN_ARCH`, resolved SDK/CRT versions, and a digest of cargo-xwin's resolved sysroot manifest. GitHub-hosted release builds require the hosted runner image identity; local and explicit self-hosted builds may omit it. Provenance is captured on the artifact build node and carried unchanged into the aggregate release manifest; the publish node does not reconstruct it. Publication is allowed only after all product manifests exactly match the declared release plan, all product archives verify against both their declared contents and digests, every required companion source asset verifies against its declared payload/source mapping and digest, and every product/source manifest is tied to the same cclover-mon Git commit. `tools/release/publication.ts` then treats that verified aggregate `ReleaseSummary` as the only expected remote publication state: it verifies that the remote tag resolves to the same source commit, creates or reuses a non-public GitHub draft, removes unexpected draft assets, replaces every expected product and companion asset from the verified local set, verifies the exact remote asset-name and size set plus SHA-256 whenever GitHub exposes an asset digest, rechecks tag identity, and only then publishes the draft. Failed draft mutation remains retryable; a rerun converges on the same expected state. An already-public release is never mutated automatically: an exact match is a no-op success and any mismatch fails closed. GitHub Actions serializes publication mutations per repository/tag while leaving build jobs independent. `validate.ts` remains the independent validation-plan authority; release orchestration may invoke repository validation but does not duplicate its command definitions.

`tools/release/linux-runtime-abi.ts` is the executable compatibility authority for official x86_64 Linux release artifacts. The release workflow fixes Linux build jobs to `ubuntu-22.04`, and authoritative Linux userspace evidence is derived from the recorded GitHub-hosted `ubuntu22` runner identity plus its durable image version rather than from a host-reported distribution name. Local and self-hosted Linux builds remain valid development artifacts and may pass archive/integrity verification, but they are not eligible for official publication because their host-native Cairo, X11, Wayland, GLib, and other non-versioned native-library generations are outside repository control. Build-time validation fails early when an explicitly GitHub-hosted Linux release build does not match the same userspace rule, while publication reuses that single rule and rejects any uncontrolled Linux provenance before GitHub release mutation. The final `dist` ELF is independently checked before packaging: its interpreter must be `/lib64/ld-linux-x86-64.so.2`, direct `GLIBC_*` imports may not exceed 2.35, direct `GCC_*` imports may not exceed 4.2.0, `GLIBC_PRIVATE` is forbidden, and the existing `libbpf.so.1` / `LIBBPF_1.0.0` contract remains the one libbpf-specific authority. The GCC ceiling represents the oldest runtime-symbol generation currently required by the declared Ubuntu 22.04 userspace baseline and shipped artifacts; raising it is therefore a compatibility-policy change rather than a linker-side implementation detail. Each product also owns an allowed upper set of direct `DT_NEEDED` SONAMEs: removing an existing dependency is allowed without policy churn, while introducing a new mandatory runtime library requires an explicit policy change. NVML remains outside that allowed set because it must stay optional and dynamically loaded. Official Linux compatibility therefore requires both controlled userspace provenance and the resulting ELF ABI evidence; raising any governed floor, adding a mandatory runtime dependency, changing the hosted Linux userspace generation, or adding another authoritative build environment is an explicit deployment-compatibility decision.

The workspace owns one shared package version in `[workspace.package]`; publishable packages inherit it. A release tag must be exactly `v<workspace-version>`. Linux server archives include the versioned systemd unit and optional eBPF capability drop-in. Windows server archives include the SCM installation script. Windows product archives include applicable third-party license/notice material plus a human-readable mapping from each embedded PawnIO payload to its release-level corresponding-source asset. The same GitHub release publishes deterministic PawnIO/PawnIO.Modules source companion archives from exact pinned upstream commits, recursively including source submodules at their recorded gitlink commits; the aggregate release manifest records each product artifact's fulfillment mapping, top-level and submodule source provenance, source-producing Git/tar/gzip tool identity, and each asset SHA-256. Source retention uses `CCLOVER_MON_DEPS_CACHE` when set and otherwise `~/.cache/cclover-mon/deps`; representation schemas occupy separate `release-sources/<schema>` namespaces, and source-plan cache identity is derived only from the deduplicated set of immutable repository-plus-commit entries rather than incidental plan metadata. `bun release.ts sources --offline` requires cache-only acquisition and therefore proves that already-retained source material can regenerate the companion assets without upstream access. Missing or mismatched fulfillment evidence and retained-source corruption fail closed before publication.

Linux and Windows builds include only their selected platform backend. Both native desktop paths consume the same `cclover-ui::Scene` contract. Windows uses Win32/GDI. Linux uses native Wayland layer-shell or X11 hosting with shared Cairo drawing. Neither native desktop path depends on Iced, winit, or wgpu. The same Linux process registers its system tray item through StatusNotifierItem on the desktop session D-Bus; no tray helper daemon or secondary executable is introduced. External native runtime libraries depend on the selected renderer and optional metric integrations.

Windows deployment supports both `x86_64-pc-windows-msvc` and `i686-pc-windows-msvc`. Platform integration code must therefore remain pointer-width correct rather than assuming 64-bit Win32 handle or style types.

The Windows distribution remains a single published `cclover-mon.exe` when PawnIO-backed sensors are enabled. Build preparation embeds only the verified production driver package required by the target plus signed Pawn modules used by implemented collectors; upstream installers, debug/test payloads, unrelated architectures, and `PawnIOLib.dll` are not runtime artifacts.

One repository-owned dependency declaration pins PawnIO provenance, target/OS mappings, selected component digests, module versions, and required module digests. Preparation owns network access and a user-scoped cache outside the worktree; Rust compilation embeds only prepared verified bytes.

PawnIO provisioning is machine-level, idempotent, and separate from sampling; runtime access is process-level and follows the installed device policy. Unsupported or denied combinations degrade only PawnIO-backed sensors. Detailed compatibility, elevation, upgrade, signature, cleanup, supply-chain, and redistribution rules are owned by [ADR 009](../09-architecture-decisions/009-windows-pawnio-provisioning.md). Project-owned source is `GPL-2.0-or-later`; vendored source and embedded third-party payloads retain their upstream licensing obligations. A Windows target containing GPL-2.0-only Linux hwmon source is distributed under GPLv2-compatible terms for the combined work.

Selected Linux hwmon source is vendored into the repository, so ordinary builds do not clone or fetch the Linux kernel. Upstream synchronization is a separate maintenance action using an external user-scoped partial/sparse Git cache and an exact pinned Linux commit; build inputs remain the checked-in source snapshot. Imported GNU C units compile as Windows objects through the compatibility boundary and link into the same executable under Cargo's build authority.

Every cargo-xwin invocation for this project must carry `XWIN_ARCH=x86,x86_64` on that exact command line, regardless of whether the immediate Rust target is 32-bit or 64-bit. Do not rely on an earlier `export`, shell/session state, or profile configuration. The setting controls which Microsoft CRT/Windows SDK architectures cargo-xwin materializes, not the Rust target itself. Keeping this value stable gives both supported Windows targets one shared cache layout and avoids cargo-xwin falling back to its different default architecture set or re-preparing the cache when the setting changes. Build instructions and automation must not omit, narrow, or otherwise vary this value per target.

The Windows executable uses the GUI PE subsystem so desktop launches do not create a console window. At startup it attaches to an existing parent console when available; terminal-facing modes such as `--tui` and diagnostic CLI commands allocate a console only when no parent console exists. Automatic frontend selection observes the attached parent console rather than allocating a console merely to make TUI appear available. This preserves the single-executable, composable-frontend model without making desktop-only launches behave like console applications.

The interactive `cclover-mon` executable can expose desktop, terminal, and HTTP frontends in any combination. With no frontend flag the application composition root selects the desktop frontend when the native desktop host reports an interactive desktop environment, otherwise selects TUI when stdin and stdout are interactive terminals, and otherwise fails with an explicit-frontend diagnostic. Desktop takes precedence when both capabilities are present. Once any of `--desktop`, `--tui`, or `--http` is present, automatic selection is disabled and only explicitly selected frontends run. Capability detection does not provide runtime fallback: failure after a frontend has been selected is reported as that frontend's startup failure. All enabled frontends share the process's single sampler and completed state stream. `cclover-mon-server` has no desktop/TUI frontend selection: starting it starts the HTTP monitor, bound to `127.0.0.1:9847` unless `--bind` is explicit.

The default/full `cclover-mon` build enables the root `http` and `ebpf-io` Cargo features. HTTP is implemented by the shared `cclover-http` crate, which uses `cclover-web-ui` to lower the shared `cclover-ui` dashboard tree to HTML/SVG and serves a small static JavaScript EventSource adapter plus CSS. It does not build or embed WebAssembly and requires no `wasm32` target, `wasm-bindgen`, Node.js runtime, external Web server, sidecar process, or additional deployed file. On Linux, `ebpf-io` compiles the attribution BPF programs and links libbpf. A supported minimal interactive build uses `--no-default-features`; it skips the optional HTTP renderer and eBPF build toolchain, rejects `--http`, and exposes process I/O attribution as disabled while leaving unrelated collectors and frontends available. The server product is a separate package rather than another root feature combination; it directly depends on the shared HTTP/runtime crates and does not pull in `cclover-desktop` or `cclover-tui`. The default listener remains loopback-only; LAN exposure requires an explicit bind override.

The userspace compatibility baseline for Linux `ebpf-io` artifacts is libbpf 1.0.0 in the `libbpf.so.1` ABI generation. Direct ELF imports must not require a `LIBBPF_*` symbol version newer than `LIBBPF_1.0.0`; repository validation checks both the SONAME and imported symbol versions on built executables. An API newer than that baseline may be used only as an optional acceleration that does not become a loader requirement and that preserves the established behavior when unavailable. Raising this baseline is a deployment-compatibility decision, not an incidental consequence of building on a newer development machine.

Full Linux builds embed the eBPF programs for the backend to load at runtime. Production startup does not invoke BCC, Python, clang, LLVM, `iotop`, `nethogs`, or another monitoring executable.

NVIDIA GPU telemetry is an optional Linux runtime integration. The executable dynamically loads `libnvidia-ml.so.1` when present; packaging must not make NVML a mandatory loader dependency. Systems without the library, without NVIDIA devices, or with an unusable NVML installation run normally and expose no NVML-derived GPU entries. Supported utilization, VRAM, temperature, power, core-clock, and fan fields are read in-process; collection must not require `nvidia-smi`, a helper daemon, or elevated process authority.

Windows vendor GPU telemetry is likewise optional and dynamically loads the runtime supplied by the installed display driver: NVIDIA `nvml.dll`, or AMD `atiadlxx.dll` / `atiadlxy.dll` according to process bitness. cclover-mon redistributes neither vendor runtime. Missing or unusable vendor libraries leave only that source unsupported without affecting other Windows collectors. The Windows process retains one session/device set per available vendor source rather than loading or rediscovering driver libraries per sample.

Where Linux per-process I/O attribution is enabled, deployment must satisfy the kernel and privilege requirements of the chosen libbpf CO-RE fentry/fexit attachments. On supported modern kernels this means readable kernel BTF plus `CAP_BPF` and `CAP_PERFMON` (and a sufficient locked-memory limit where the kernel/libbpf combination still requires it). These are prerequisites for attribution metrics, not for unrelated collectors. Packaging may grant the narrow capabilities to the executable or use an equivalent launcher policy; it must not make unrestricted root execution the normal requirement. A compatibility path requiring broader authority must be explicit and separately justified.

Failure to satisfy those prerequisites leaves the affected I/O-attribution metric unavailable while the rest of the single application process continues to run.

The headless server participates in normal service-manager lifecycle rather than daemonizing itself. On Unix, foreground SIGINT/SIGTERM request cooperative shutdown; the supplied systemd unit relies on SIGTERM and uses a dynamic unprivileged `cclover-mon` account, so installation does not require pre-creating a service user. Optional eBPF capabilities are a separate systemd drop-in rather than a reason to run the whole monitor unrestricted as root. On Windows, `--service` registers the process with the Service Control Manager and maps STOP/SHUTDOWN controls to the same cooperative shutdown primitive. The interactive product's HTTP-only foreground path uses the same shutdown model rather than parking the main thread indefinitely. HTTP `/healthz` reports listener liveness; `/readyz` and `/api/v1/*` remain unavailable until the first real sampled state has been published, so startup never fabricates readiness from a default `MonitorState`.
